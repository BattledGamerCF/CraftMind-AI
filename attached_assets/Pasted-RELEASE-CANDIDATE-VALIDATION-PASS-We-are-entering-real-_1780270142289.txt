RELEASE CANDIDATE VALIDATION PASS

We are entering real-world testing. Do NOT add new features, new AI systems, new planners, new memories, new playstyles, new providers, or new architecture.

Goal:
Make the project as reliable and testable as possible before Minecraft testing begins.

Rules:
- Prioritize fixing bugs over adding capabilities.
- Prioritize startup reliability over feature development.
- Prioritize user experience over developer convenience.
- Remove unnecessary complexity if it improves stability.
- Minimize file reads and avoid expensive audits unless necessary.
- Operate in Economy mode style: targeted edits only.

Perform the following:

PHASE 1 - STARTUP VALIDATION

Audit the complete startup flow:

double-click launcher
launcher startup checks
.env creation
API startup
dashboard startup
browser auto-open
bot creation

Verify there are no dead paths, missing files, broken imports, missing env vars, or assumptions that would fail on a clean machine.

Fix any issues found.

PHASE 2 - DASHBOARD USABILITY

Review the dashboard as if the user has never touched Node, npm, GitHub, Mineflayer, or Minecraft bot software before.

Look for:

- confusing labels
- missing tooltips
- unclear error messages
- forms that can submit invalid values
- missing loading indicators
- actions with no feedback
- places where the user can become stuck

Fix only high-value usability problems.

PHASE 3 - MINECRAFT COMPATIBILITY CHECK

Audit version handling.

Verify:

- version field passes correctly from UI → API → bot
- auto-detect behavior works
- latest supported versions display correctly
- unsupported versions fail gracefully

Do not add support for new versions.
Only validate and harden existing behavior.

PHASE 4 - ERROR RECOVERY

Check all major failure cases:

- invalid host
- invalid port
- server offline
- authentication failure
- provider unavailable
- Ollama offline
- dashboard cannot reach API
- queue full
- planner failure

Ensure users receive actionable messages instead of stack traces or silent failures.

PHASE 5 - TESTING SUPPORT

Improve TESTING.md if necessary.

For each test case:

- setup
- action
- expected result
- pass criteria

Make sure a normal user can follow it.

PHASE 6 - CLEANUP

Remove:

- unused imports
- unused helper functions
- stale TODOs
- dead code discovered during this validation pass

Do not remove intentionally documented architecture files.

PHASE 7 - FINAL REPORT

Produce:

1. Bugs fixed
2. Files changed
3. Remaining warnings
4. Anything that should be tested manually in Minecraft before public release

No new features.
No architecture expansion.
No speculative improvements.

Focus entirely on release readiness and real-world reliability.
