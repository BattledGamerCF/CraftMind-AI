The architecture is now large enough that development efficiency and controlled reasoning depth matter more than raw feature velocity.

From this point forward, optimize your own development workflow for:
- smaller diffs
- incremental edits
- lower token usage
- reduced parallel overengineering
- fewer unnecessary rewrites
- faster verification cycles
- isolated subsystem modifications

Do not rebuild or refactor unrelated systems when implementing a feature.

Before making changes:
1. Analyze which exact files and systems are affected
2. Minimize the modification surface
3. Reuse existing abstractions whenever possible
4. Avoid speculative architecture expansion unless explicitly requested

Prefer:
- extending existing systems
- adding focused modules
- targeted refactors
over:
- large-scale rewrites
- framework migrations
- broad architectural churn

When implementing features:
- patch surgically
- preserve interfaces
- avoid touching stable systems unnecessarily
- avoid rewriting working code for style consistency alone

Reduce expensive autonomous “parallel mega-refactor” behavior unless the task genuinely requires it.

For simple tasks:
- reason briefly
- implement directly
- verify quickly

For medium tasks:
- plan internally
- isolate dependencies
- implement incrementally
- test affected systems only

For complex/high-risk tasks:
- enter “Auto Reasoning Mode”

Auto Reasoning Mode:
- activates only for architecturally difficult or ambiguous tasks
- allowed to spend more reasoning effort
- performs deeper dependency analysis
- checks for cascading side effects
- verifies interfaces before modification
- prefers staged implementation over massive one-pass rewrites

Auto Reasoning Mode should trigger for:
- planner/arbitrator changes
- concurrency issues
- memory architecture changes
- multi-agent coordination
- persistence systems
- networking changes
- task scheduling logic
- large API refactors

Auto Reasoning Mode should NOT trigger for:
- UI tweaks
- endpoint additions
- simple executors
- small bug fixes
- telemetry fields
- config changes
- small behavior patches

When reasoning deeply:
- summarize conclusions compactly
- avoid verbose chain-of-thought dumping
- output concise implementation plans instead of long narration

Prefer execution over narration.

Additionally, begin implementing runtime “Cognitive Economy Modes” for the bot itself.

Target modes:
- deterministic
- lightweight
- balanced
- auto
- deep-reasoning

Mode behavior:

deterministic:
- no LLM usage unless explicitly addressed

lightweight:
- small local models only
- short prompts
- compressed memory

balanced:
- current default behavior

auto:
- dynamically escalates reasoning depth depending on:
  - ambiguity
  - planning complexity
  - novelty
  - urgency
  - required creativity
  - reaction-time sensitivity

deep-reasoning:
- slower but more capable
- allowed to use larger prompts/models
- intended for:
  - structure generation
  - strategic planning
  - large cooperative tasks
  - novel problem solving

Important:
If a task requires rapid reaction time:
- prefer deterministic systems
- avoid long reasoning delays

If a task is long-horizon and non-urgent:
- allow deeper reasoning

Example:
Combat:
- deterministic/reactive

“Build an efficient medieval mining town integrated into this mountain biome”:
- auto or deep reasoning mode

Add the mode system without disrupting the existing Planner → Arbitrator → Executor boundary.

Do not allow any reasoning mode to bypass deterministic validation or execution systems.
